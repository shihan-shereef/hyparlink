BUG-1 & BUG-2: Background Tab Video Freezing & Audio/Video Desynchronization
--------------------------------------------------------------------------------
- Component: Local MediaRecorder & Canvas Draw Engine
- Severity: High / Critical for Recording Fidelity
- User Reported Behavior:
  * Bug-1: When performing local recording, switching to another browser tab or 
    minimizing the window freezes the video recording. There is zero movement in the 
    video until the user returns to the active recording tab.
  * Bug-2: While the video pauses/freezes in the background tab, the audio microphone 
    continues recording normally without any interruption, producing an output video 
    where audio plays continuously while the visuals remain frozen on a single still frame.

- Technical Root Cause:
  1. Modern browser engines (Chromium, WebKit, Gecko) implement aggressive power-saving 
     and CPU-throttling policies for background/inactive tabs.
  2. If the local video recorder captures its stream via `<canvas>.captureStream(fps)`, 
     the canvas frame update loop typically relies on `window.requestAnimationFrame()`.
  3. When the tab loses focus (`document.hidden === true`), `requestAnimationFrame()` 
     is completely paused by the browser engine, preventing new video frames from being 
     drawn to the canvas. Consequently, the video track of the `MediaStream` halts.
  4. Conversely, the `AudioContext` and hardware microphone `MediaStreamTrack` operate 
     on independent OS-level audio clock threads that are exempt from visual render throttling. 
     This causes severe A/V desync where the audio track records real-time audio while the 
     video track remains frozen at the timestamp when the tab was hidden.

- Steps to Reproduce:
  1. Open Ollasync in a desktop browser and initiate a local recording session.
  2. Speak aloud while waving hands in front of the camera.
  3. Switch to another browser tab for 15 seconds while continuing to speak.
  4. Return to the Ollasync recording tab, record for 5 more seconds, and stop recording.
  5. Play back the resulting recording: observe that during seconds 0-15 of tab absence, 
     the speaker's voice is heard continuously, but the video is frozen on the last frame.

- Technical Remediation & Implementation Plan:
  1. Web Worker Clock Fallback:
     Implement a dedicated Web Worker timer (`setInterval` / `postMessage` tick) that 
     does not undergo background throttling. When `document.visibilitychange` fires and 
     `document.hidden` becomes true, immediately switch the canvas render ticker from 
     `requestAnimationFrame()` to the Web Worker interval (e.g., 30 ticks/second).
  2. OffscreenCanvas Architecture:
     Migrate canvas rendering to an `OffscreenCanvas` inside a Web Worker. Web Worker 
     threads are not bound to window display refresh cycles and maintain continuous frame 
     generation even when the main thread window is obscured or minimized.
  3. Direct MediaStream Recording:
     If no canvas overlays are active, record the raw camera `MediaStreamTrack` directly 
     using `MediaRecorder` rather than piping through a canvas element.

BUG-3 & BUG-4: Virtual Background Blackout & Guest Stream Freeze (Blur, Ocean, Slate)
--------------------------------------------------------------------------------
- Component: Virtual Background Filter Pipeline / WebRTC Track Swap
- Severity: High / Blocker for Live Video Calls
- User Reported Behavior:
  * Bug-3: Tapping on background Blur, Ocean, or Slate causes the host camera preview 
    to go completely dark/black. On the remote guest screen, the host video freezes 
    and remains blank/nil. The host is forced to toggle the camera off and on to recover.
  * Bug-4: When tapping Blur, Ocean, or Slate, the video freezes and displays only a frozen 
    still frame. Turning the camera off and back on while the background filter remains selected 
    causes the filtered background to finally start working.

- Technical Root Cause:
  1. Pipeline Initialization Delay:
     When the host selects a virtual background, the application instantiates the background 
     segmentation model (e.g. MediaPipe Selfie Segmentation, BodyPix, or WebGL shader). 
     This loading phase is asynchronous and takes between 400ms to 1800ms.
  2. Premature Track Replacement:
     The host's WebRTC RTCRtpSender immediately calls `sender.replaceTrack(processedCanvasTrack)` 
     BEFORE the segmentation engine has processed its first valid frame. 
     At this moment, the output canvas context has not completed initialization, producing 
     either a null surface or a cleared black frame buffer (`gl.clearColor(0,0,0,1)`).
  3. WebRTC Stream Stalling:
     Because the canvas stream has no initial valid video frames flowing, the WebRTC peer 
     connection stalls the video track. The remote peer's decoder receives no keyframes and 
     maintains the last valid frame buffer in a frozen state.
  4. Why Camera Off/On Recovers:
     When the user clicks Camera Off, the track is cleanly stopped. When Camera On is clicked, 
     the segmentation model is ALREADY fully loaded in memory, allowing `getUserMedia` to 
     feed valid camera frames immediately through the already-initialized shader, which 
     sends active frames to the canvas without a cold-start freeze.

- Steps to Reproduce:
  1. Join an Ollasync call with Host and Guest connected.
  2. As Host, open the background effects panel and click "Blur", "Ocean", or "Slate".
  3. Observe Host screen: camera preview goes black.
  4. Observe Guest screen: Host video freezes immediately on the last pre-effect frame.
  5. As Host, toggle the camera button Off and then On: observe that the video resumes 
     with the selected background effect active.

- Technical Remediation & Implementation Plan:
  1. Seamless Pipeline Warming & Delayed Track Swap:
     Keep the existing live camera track streaming to the WebRTC connection while the 
     segmentation model and background textures load in the background.
  2. First-Frame Ready Guard:
     Do NOT call `sender.replaceTrack()` until the segmentation canvas confirms at least 
     3 consecutive valid processed frames have been rendered:
     ```typescript
     let readyFrames = 0;
     segmenter.onFrameRendered = () => {
       readyFrames++;
       if (readyFrames === 3) {
         peerConnection.getSenders().forEach(sender => {
           if (sender.track?.kind === 'video') sender.replaceTrack(processedCanvasTrack);
         });
       }
     };
     ```
  3. Fallback Pass-Through:
     If shader compilation or texture loading fails, fall back gracefully to the raw camera 
     feed with an informative UI toast rather than delivering a blank black canvas.

BUG-5: Custom Background Upload Blank Screen & Camera Toggle Dependency
--------------------------------------------------------------------------------
- Component: Custom Asset Ingestion & WebGL Texture Binding
- Severity: Medium / High Usability Impact
- User Reported Behavior:
  When uploading or applying a custom background image from the host side, the video 
  immediately goes blank/black. The host must toggle the camera off and on before the 
  custom background image appears and functions.

- Technical Root Cause:
  1. Uncaught Image Decoding & CORS Latency:
     When a custom image file (JPG/PNG) is uploaded or selected, the `HTMLImageElement` 
     is assigned an Object URL (`URL.createObjectURL(file)`). The WebGL texture creation 
     subroutine attempts to call `gl.texImage2D(..., image)` synchronously before 
     `image.decode()` or `image.onload` has completed.
  2. WebGL Invalid Texture State:
     Binding an incomplete image resource throws a silent WebGL error or binds an empty 
     1x1 black texture, breaking the composition shader pass and resulting in an all-black frame.
  3. Toggling camera off and on unbinds and re-initializes the shader pass after the image 
     element has finished loading and caching in memory, allowing the texture to bind successfully.

- Steps to Reproduce:
  1. In Ollasync, click "Custom Background" and select a high-resolution image file.
  2. Observe that the camera feed turns completely black on both host and guest views.
  3. Click Camera Off, then Camera On: the custom background now appears correctly behind the user.

- Technical Remediation & Implementation Plan:
  1. Await Asynchronous Image Decoding Before Shader Binding:
     ```typescript
     async function setCustomBackground(fileOrUrl: File | string) {
       const img = new Image();
       img.crossOrigin = "anonymous";
       img.src = typeof fileOrUrl === "string" ? fileOrUrl : URL.createObjectURL(fileOrUrl);
       await img.decode(); // Ensures full bitmap decode before WebGL upload
       webglPipeline.updateBackgroundTexture(img);
     }
     ```
  2. Preserve Live Camera Stream Until Background Texture Is Ready:
     Do not switch the video pipeline context until `img.decode()` succeeds. If decode 
     fails, maintain the current background effect and alert the user.

BUG-6: Real-Time Translation Latency (2–3 Second Perceived Delay)
--------------------------------------------------------------------------------
- Component: Speech-to-Text (STT) Chunking & Machine Translation Pipeline
- Severity: Medium / Conversation Flow Friction
- User Reported Behavior:
  In live translation mode, there is an audible/visual lag of 2 to 3 seconds before 
  translated subtitles appear on screen, creating an awkward delay during live conversations.

- Technical Root Cause:
  1. Overly Long Voice Activity Detection (VAD) Silence Window:
     The audio segmentation engine waits for a complete sentence or an extended silence 
     threshold (1500ms–2000ms) before dispatching the recorded PCM buffer to the ASR service.
  2. Non-Streaming Translation Architecture:
     The server processes transcripts via sequential request-response HTTP cycles:
     `Audio Chunk -> Whisper/ASR (800ms) -> LLM Translation API (800ms) -> Subtitle WebSocket (200ms)`.
     The sum of VAD silence buffering + ASR transcription + sequential LLM translation 
     yields a total round-trip latency of 2500ms–3200ms.

- Steps to Reproduce:
  1. Enable live subtitles and speech translation in an Ollasync call.
  2. Speak a short phrase: "Hello, how are you today?"
  3. Observe the stopwatch: the translated subtitle only appears 2.5 to 3.2 seconds after 
     the phrase was uttered.

- Technical Remediation & Implementation Plan:
  1. Implement Streaming Partial Hypotheses:
     Replace sentence-boundary batching with streaming ASR (e.g. WebSocket streaming with 
     250ms audio slices). Display real-time interim speech transcripts immediately (<300ms).
  2. Token-Level Streaming Translation:
     Pipe partial ASR tokens directly to a streaming translation model via Server-Sent Events 
     (SSE) or WebSockets. This reduces perceived first-word translation latency to under 800ms.
  3. Client-Side VAD Calibration:
     Reduce the silence trailing window from 2000ms down to 600ms–800ms for conversational speech.

BUG-7: Mobile Landscape Viewport Clipping ("Caption Off" Button Inaccessible)
--------------------------------------------------------------------------------
- Component: Mobile Responsive Layout & Safe Area CSS
- Severity: Medium / Accessibility Defect on Mobile Browsers
- User Reported Behavior:
  When holding a smartphone in landscape (horizontal) orientation in the browser, 
  the "Caption Off" button is cut off / invisible at the bottom of the screen, preventing 
  mobile users from disabling captions.

- Technical Root Cause:
  1. Landscape Viewport Compression:
     In mobile landscape mode, vertical screen height is heavily restricted (e.g., 375px–414px height). 
     Browser navigation bars (Safari address bar, Chrome URL pill) consume 60px–90px of vertical space.
  2. Missing `env(safe-area-inset-bottom)` & Overflow Wrapping:
     The bottom control toolbar uses a fixed `bottom: 0; height: 64px;` layout with 
     `overflow: hidden; flex-wrap: nowrap;`.
     The "Caption Off" button sits at the end of the flex container and gets pushed 
     either off-screen horizontally or occluded vertically beneath the mobile browser's 
     floating bottom controls.

- Steps to Reproduce:
  1. Open Ollasync on an iPhone or Android smartphone in Safari or Chrome.
  2. Join a video call and rotate the phone horizontally into landscape mode.
  3. Enable captions.
  4. Attempt to turn off captions: observe that the "Caption Off" button is not visible 
     in the control bar or is clipped beneath the bottom viewport edge.

- Technical Remediation & Implementation Plan:
  1. Responsive Landscape CSS Media Query:
     Add a dedicated landscape rule for compressed viewports:
     ```css
     @media (max-height: 520px) and (orientation: landscape) {
       .meeting-control-bar {
         height: 48px !important;
         padding-bottom: max(6px, env(safe-area-inset-bottom)) !important;
         overflow-x: auto !important;
         -webkit-overflow-scrolling: touch;
       }
       .meeting-control-bar button {
         padding: 4px 8px !important;
         font-size: 11px !important;
         min-width: 36px !important;
       }
     }
     ```
  2. Caption Toggle Secondary Placement:
     Include a quick-access caption toggle directly on the video overlay area or inside 
     the 3-dots "More Options" bottom sheet so users are never blocked if toolbar width is constrained.

A. Solved "No Color, Black Silhouettes, and 16px Serif Font" in Master Render
--------------------------------------------------------------------------------
- Root Cause:
  The Stride shoe ad HTML header contained instructional comments referencing `<style>`:
  `* Colours ........ the :root block at the top of <style>`
  The regex `/<style[^>]*>([\s\S]*?)<\/style>/gi` in `create-video/page.tsx` and 
  `server.mjs` matched starting inside the comment, capturing comment text plus `-->`, 
  `<meta>`, `<title>`, `<link>` into `styles.css`.
  Headless Chromium discarded `:root` due to the syntax error.
  * All SVG color variables dropped to SVG default pure black (`rgb(0, 0, 0)`).
  * Shorthand `font: 900 78px/1.08 var(--font)` failed, reverting to 16px Times New Roman.
  * Yellow accent `em { color: var(--accent); }` lost `--accent`, defaulting to white text.

- Auto-Repair Loop Bug:
  Clicking "Auto-Repair" re-ran the unmasked extraction on the client, perpetually 
  re-corrupting `styles.css`.

- Engineering Fix Applied:
  1. HTML Comment Masking: Protected `<!-- ... -->` before extracting `<style>`/`<script>`.
  2. `sanitizeCssText`: Added multi-stage CSS sanitizer stripping stray `-->`, `<meta>`, 
     `<title>`, `<link>`, and invalid leading tokens across `page.tsx`, `server.mjs`, 
     and `design-validator.ts`.
  3. Recompiled `ai-composition-generator` TypeScript.
  4. Re-rendered with HyperFrames: verified full color reproduction (`#ffd23f` accent, 
     `#3f86d6` sky, `#ff5533` shirt) and 78px Poppins typography.
  5. Overwrote storage `video.mp4` and updated `thumbnail.jpg`.
