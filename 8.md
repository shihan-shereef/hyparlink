## 1. Storage Provider Selected

The storage architecture implements a **multi-provider pluggable abstraction** supporting:
1. **Cloudflare R2** (`STORAGE_PROVIDER=r2`)
2. **AWS S3** (`STORAGE_PROVIDER=s3`)
3. **Convex Storage** (`STORAGE_PROVIDER=convex`)
4. **Local Development Storage** (`STORAGE_PROVIDER=local` / default fallback)

In local development and automated CI testing environments without pre-configured cloud credentials, **Local Development Storage** operates as the default fallback. For production setups, **Cloudflare R2** or **AWS S3** are configured via environment variables.

---

## 2. Why It Was Selected

1. **Vendor Independence**: The application is not locked into any single cloud provider. Teams can switch between Cloudflare R2 (zero egress fees), AWS S3 (industry standard), or native Convex Storage without altering application business logic.
2. **Zero-Configuration Local Development**: Developers can clone the repository and run full end-to-end rendering and video streaming flows offline or without cloud API keys.
3. **S3 API Compatibility**: Both Cloudflare R2 and AWS S3 share the unified `@aws-sdk/client-s3` and `@aws-sdk/s3-request-presigner` SDKs, minimizing bundle overhead and maintaining standard S3-compatible patterns.
4. **HTTP 206 Byte-Range Streaming**: All providers (including the local provider) implement HTTP Range request handling, allowing HTML5 `<video>` players to scrub, seek, pause, and stream video chunks seamlessly.

## 7. Upload Flow

1. **Rendering Completes**: HyperFrames outputs the local MP4 (e.g. `/outputs/output-xxx.mp4`).
2. **Predictable Key Generation**:
   `workspaces/{workspaceId}/projects/{projectId}/renders/{jobId}/video.mp4`
3. **Webhook Progress**: Backend emits `job.progress` with `status: "uploading"` to Convex.
4. **Streaming Upload**: Provider streams the file via `fs.createReadStream(localPath)` directly to the object store with `ContentType: "video/mp4"` and `Cache-Control: "public, max-age=31536000, immutable"`.
5. **Upload Verification**: `provider.verifyUpload()` inspects the stored object's metadata (existence and byte count matching the local file within tolerance).
6. **URL Resolution**: Persistent URLs (`storageUrl` and `cdnUrl`) are generated.
7. **Convex Update**: Completion webhook updates the Convex job and project with all storage metadata.
8. **Local Cleanup**: If `KEEP_LOCAL_OUTPUTS` is not `"true"`, the local temporary MP4 is deleted.

## 8. CDN Configuration

When configured with Cloudflare R2 or AWS S3 + CloudFront:
- **Cloudflare R2 CDN**:
  - `R2_PUBLIC_URL=https://cdn.hyperframes.com`
  - URL format: `https://cdn.hyperframes.com/workspaces/{ws}/projects/{proj}/renders/{job}/video.mp4`
  - Cloudflare Edge automatically caches immutable videos (`Cache-Control: public, max-age=31536000, immutable`) and handles byte-range requests directly from edge points-of-presence (PoPs).
- **AWS S3 + CloudFront**:
  - `S3_PUBLIC_URL=https://d123456789.cloudfront.net`
  - CloudFront distribution configured with S3 origin access control (OAC).

## 9. Signed URL Implementation

For private buckets, Convex exposes the authenticated query `getVideoPlaybackUrl`:

```typescript
export const getVideoPlaybackUrl = query({
  args: { projectId: v.id("projects") },
  handler: async (ctx, args) => {
    const project = await ctx.db.get(args.projectId);
    // Verifies workspace access and user permissions
    // Returns short-lived signed URL (e.g. expires in 1 hour)
    return {
      playbackUrl: signedUrl,
      expiresAt: Date.now() + 3600 * 1000,
      isDirectCdn: false
    };
  }
});
```

## 10. Security Implementation

1. **Multi-Tenant Workspace Isolation**:
   All storage object keys are scoped by workspace:
   `workspaces/{workspaceId}/projects/{projectId}/...`
2. **Access Control**: Users can only generate playback URLs or mutate projects belonging to workspaces where they hold active membership.
3. **No Secret Exposure**: Cloud access keys (`R2_SECRET_ACCESS_KEY`, `S3_SECRET_ACCESS_KEY`) remain strictly on the backend service and are never sent to the browser or stored in Convex documents.
4. **Path Traversal Protection**: Local storage provider validates all incoming object paths to guarantee they remain strictly within the root storage directory, returning `403 Forbidden` for traversal attempts (`../`).

---

## 11. Cleanup Implementation

When a project is deleted:
1. Convex deletes the project record.
2. If `storageKey` is present, a cleanup request invokes `provider.delete(storageKey)`.
3. The storage object is permanently removed from the bucket/disk.
4. Associated file metadata records are unlinked.

---

## 12. Retry Implementation

When a user retries generation for a project:
1. A new unique `jobId` is allocated (e.g. `job-002`).
2. The render is written to a distinct object key:
   `workspaces/{ws}/projects/{proj}/renders/job-002/video.mp4`
3. Previous renders are not blindly overwritten, preventing race conditions or cache corruption.
4. Upon successful upload of the new render, Convex updates the project record to reference the latest successful storage key and URLs.

## 19. Known Limitations

1. **Direct Video Transcoding**: Outputs are currently rendered directly as H.264/MP4 by HyperFrames. HLS / DASH multi-bitrate adaptive streaming chunking (m3u8 playlists) is not yet integrated.
2. **Convex Storage File Size Limits**: Large video renders (> 300MB) are better suited for Cloudflare R2 or AWS S3 than Convex's internal file storage due to blob upload size limits.
